# 毫秒级量化系统：数据库选型与分层架构方案

> 场景标签：金融服务 · 量化系统基础设施
> 输出日期：2026-10-14
> 性质：技术架构选型建议，不含任何投资建议

---

## 结论先行（TL;DR）

- **不存在一个"毫秒级数据库"能包打天下。** 毫秒级读写是**架构问题**，不是选库问题。正确做法是分成 5 层，每层用不同的东西，甚至第 0 层**根本不用数据库**。
- **下单链路禁止查数据库。** 即使嵌入式 SQLite 一次写入也要几十微秒，一次跨进程查询就是毫秒级——这在毫秒策略里是致命的。持仓/风控状态必须常驻内存，盘后异步落盘，崩溃用日志回放恢复。
- **行情与因子中枢（主力库）**：国内私募/券商做 A 股中高频，**首选 DolphinDB**（流批一体，回测代码直接上生产）；海外 HFT 或已有 q 语言团队的，选 kdb+ / KDB-X；预算有限、以 Python 为主的中小团队，选 ClickHouse + ArcticDB。
- **账户/订单/风控（事务库）**：**PostgreSQL**，不要用 MySQL 扛大表，更不要用时序库做账务。
- **冷数据**：对象存储（S3 / MinIO）+ Parquet，别用数据库存十年历史 tick。

## 一、先把"毫秒级"拆成三件事

说"毫秒级读写"时，实际上混着三种完全不同的需求，它们的时延预算相差 3~6 个数量级，用同一个库满足全部需求必然顾此失彼：

| 环节 | 时延预算 | 数据特征 | 应该用什么承载 |
|---|---|---|---|
| 行情解码 → 信号计算 → 下单 | **微秒级**（1~100μs） | 极热、只保留最新状态、可重建 | **不用数据库**：共享内存 + 无锁队列（Disruptor / Chronicle）+ 内存订单簿 |
| 盘前风控 / 额度校验 | **微秒级** | 少量标量 | 内存标志位，预聚合风险敞口常驻内存；绝不查库 |
| Tick / 逐笔委托落盘 | 异步即可（ms~s） | append-only、海量（A 股全市场日增约 20~50GB） | 列式时序库批量写入，允许延迟落盘 |
| 实时因子 / 信号计算 | **毫秒级** | 流式增量 | 流计算引擎（DolphinDB 流表 / kdb+ tick 订阅 / Flink） |
| 历史回测 / 因子挖掘 | 秒~分钟级 | TB~PB 级、全市场长周期 | 列存 + 合理分区；或 ArcticDB / Parquet 面板数据 |
| 订单 / 持仓 / 资金账务 | 毫秒级单事务，但要求**强一致** | 小数据量、高价值 | 关系型数据库（PostgreSQL） |

> 数据来源：时延量级与数据规模参考 DolphinDB 官方技术文档《金融市场高频数据的有效管理》（全市场 L1/L2 历史约 20~50TB、日增 20~50GB）；HFT 端到端时延（行业普遍 <100μs）参考 BJMS 2025 年券商分布式系统综述（二手来源，需核实原文）。

> **一个常被忽略的前提**：如果你的行情源是免费 Level-1（3 秒快照），那么"毫秒级"毫无意义——免费 L1 与付费 L2 逐笔之间的时延差异在**百毫秒级**。先确认数据源，再谈数据库。优化数据库省下的 5 毫秒，抵不过数据源自带的 100 毫秒。

## 二、推荐的分层架构

```
┌─ L0 交易热路径 ─────── μs 级 · 不入库 ──────────────────────────┐
│ 共享内存状态机 + 无锁队列。行情解码、订单簿、信号、下单封装在同一   │
│ 进程/共享内存中；内核旁路（Onload / DPDK）收包；风控只读内存标志位。│
│ 这一层不允许出现任何数据库调用，收盘后异步持久化，崩溃靠 WAL /      │
│ 日志回放恢复。                                                    │
└──────────────────────────────────────────────────────────────────┘
┌─ L1 实时行情与因子 ─── ms 级 · 流计算 ──────────────────────────┐
│ DolphinDB（流表 + 订阅 + 时序引擎）或 kdb+。承接 tick 落盘与实时   │
│ 因子增量计算，输出信号给 L0。关键要求：流批一体——同一份因子逻辑     │
│ 同时跑历史回测和实盘流式，杜绝"研究 Python、生产 C++"两套实现导致   │
│ 的回测/实盘不一致。                                               │
└──────────────────────────────────────────────────────────────────┘
┌─ L2 历史库与因子库 ─── 秒~分钟 · TB/PB ─────────────────────────┐
│ DolphinDB / ClickHouse / ArcticDB。存全市场 L2 历史、分钟 K、因子   │
│ 面板（时间 × 标的 × 因子）。按"时间 × 标的"或"时间 × 因子名"分区：  │
│ 时序查询多用前者，横截面全市场因子更新多用后者（高频因子库常见做法   │
│ 是两者各存一份）。                                                 │
└──────────────────────────────────────────────────────────────────┘
┌─ L3 事务库 ─────────── ms 级 · 强一致 ──────────────────────────┐
│ PostgreSQL。账户、资金、持仓、订单、成交流水、策略参数、权限。要求   │
│ ACID 与可审计，用 WAL + 同步/半同步复制。TimescaleDB 可作为 PG 上的 │
│ 时序扩展，中小规模可一套打天下。                                    │
└──────────────────────────────────────────────────────────────────┘
┌─ L4 冷归档 ─────────── 小时级 · 只读 ───────────────────────────┐
│ 对象存储（S3 / MinIO）+ Parquet / HDF5。十年以上 tick 归档、合规    │
│ 留存。数据库只保留近 1~3 年热数据，历史按需挂载。压缩比参考：        │
│ DolphinDB 存 L2 数据实测约 8:1。                                   │
└──────────────────────────────────────────────────────────────────┘
```

> 架构依据：DolphinDB 官方行业方案（券商/私募）与 OceanBase 极速交易场景技术分享（全内存计算与关系库是分层协同而非替代关系）；分层协同思路为二手来源综合，需结合自建压测验证。

## 三、主流候选横向对比

| 产品 | 类型 | 时延量级 | 授权 | 强项 | 短板 / 注意 |
|---|---|---|---|---|---|
| **kdb+ / KDB-X** | 内存列存 + q 语言 | 微秒~毫秒 | 商业（KDB-X 有免费社区版，商用超限额需付费） | 海外 HFT 事实标准；asof join、tick 处理原语成熟；KDB-X 支持 Python/SQL/q 三语言与 GPU 加速 | q 语言人才稀缺、学习曲线陡；旧版单线程并发受限；国内技术支持弱 |
| **DolphinDB**（推荐） | 分布式列存 + 流计算 | 单因子 1~2μs、百因子 42μs（Swordfish 引擎官方实测） | 社区版免费；企业版商业授权 | 流批一体；2000+ 内置函数、WorldQuant 101 / 技术指标库；L2 高频因子原语；中文文档与国内支持 | 社区生态小于开源栈；GPU/异构等高级特性需商业版 |
| **ClickHouse** | 开源 OLAP 列存 | 批量扫描极快；单行写入/更新弱 | Apache 2.0 | 开源免费、扫描性能强、生态大、运维资料多 | 不适合 append-only tick 高频单行写入与实时更新；金融/时序函数通用性弱；集群支持曾受诟病 |
| **ArcticDB** | 客户端 DataFrame 库 | Python 侧秒级读写亿行 | BSL（生产部署需商业授权） | pandas 原生、无服务器（S3 / LMDB / Azure Blob）、bitemporal 版本、schema 演进友好 | 非服务端、不适合下单链路；并发写需自行规划；投研场景为主 |
| **QuestDB** | 开源时序库 | 高吞吐 ingest | Apache 2.0 | 写入吞吐高、SQL 友好、开源可商用 | 生态与企业集成少；金融专用函数有限 |
| **TimescaleDB** | PG 时序扩展 | 毫秒~秒 | 开源 / 云 | 关系 + 时序一体、运维熟悉、可复用 PG 生态 | 极致性能不如专用列存；超大规模性价比下降 |
| **InfluxDB** | 通用时序库 | — | 开源 / 商业 | 监控运维生态成熟 | 缺少量化常用函数；有机构实测性能比 DolphinDB 差约一个数量级 —— 建议只用于系统监控 |
| **PostgreSQL**（推荐） | 关系型（事务） | 单事务毫秒级 | 开源 | ACID 强一致、账务与审计可靠、生态成熟 | 列存与压缩弱，不适合海量行情分析 |
| **Redis / 内存网格** | KV / 内存数据网格 | 亚毫秒~微秒 | 开源 / 商业 | 旁路缓存、跨进程状态共享、发布订阅 | 单线程模型在高并发写下有阻塞风险；**不能承载撮合与持久化真相**，只能做旁路 |

> 来源：DolphinDB 官方文档/官网（dolphindb.cn、docs.dolphindb.cn、dolphindb.com）；kdb+/KDB-X 与 ArcticDB 定价与特性来自 7wdata 汇总页与 man.com/arcticdb（第三方汇总，**需核实原文**）；华夏基金选型评价（InfluxDB 比 DolphinDB 差一个数量级、kdb+ 昂贵且国内支持弱）来自中华网科技 2022-09-20 报道（**二手媒体来源，需核实原文**）。

## 四、三套可直接落地的组合

### 方案 A · 推荐（默认选择）

> 国内私募 / 券商 · A 股中高频 · 有预算

- L1+L2：**DolphinDB**（行情落盘 + 实时因子 + 回测一体）
- L0：自研共享内存状态机 + 无锁队列
- L3：**PostgreSQL**（账户 / 订单 / 风控）
- L4：MinIO + Parquet 归档
- 理由：中文支持、L2 高频函数现成、流批一体避免回测与实盘两套代码、国内落地案例多

### 方案 B · 极致低延迟（HFT）

> 端到端 <100μs · 有 q / C++ 团队

- L0：全内存 + 内核旁路 + FPGA 行情解析，**数据库完全不进关键路径**
- L1+L2：**kdb+ / KDB-X**，仅做盘后研究、回放与合规留存
- L3：PostgreSQL；L4：对象存储
- 理由：真 HFT 的胜负手在网络与内存布局，不在数据库；库的职责收缩为"研究 + 审计"

### 方案 C · 轻量起步（成本优先）

> 中小团队 · 分钟级 / 日频 · Python 为主

- L2：**ClickHouse**（回测扫描）+ **ArcticDB**（因子面板 / 版本管理）
- L1：QuestDB 或 Flink + Kafka 承接实时
- L3：**PostgreSQL**（+ TimescaleDB 可选）
- 理由：全开源栈、可先跑通；代价是高频 tick 写入与实时更新能力弱，做到秒级以上策略没问题

### 信号计算时延：Swordfish 引擎 vs C++

| 场景 | Swordfish 脚本 | 参照 |
|---|---|---|
| 单因子（平均） | 1.5 μs | — |
| 10 因子 | 4 μs | — |
| 100 因子 | 42 μs | C++ 实现平均约 100 μs |

> 来源：DolphinDB 官方实测《交易信号低延时计算实测》（5.8GHz 8 核服务器，100 个生产级 L2 自定义因子）。Swordfish 脚本平均时延 42μs、P99 49.6μs，同场景 C++ 实现平均约 100μs；并发从 1 路拉到 6 路平均时延仅从 46.3μs 增至 48.0μs。**厂商自测数据，需自建压测复核。**

## 六、工程红线（踩一条就白做）

1. **下单路径里不许有数据库调用。** 一次跨进程查询 = 毫秒级，嵌入式 SQLite 一次写入也要几十微秒。持仓与额度启动时预加载进内存，盘后异步落盘，中途崩溃用日志回放恢复最终一致性。
2. **回测与实盘必须同一份逻辑。** 研究用 Python、生产用 C++ 重写是量化系统最常见的翻车点——两套实现对不齐，回测收益无法复现。优先选流批一体的引擎（一份代码同时跑历史与实时）。
3. **先定分区，再灌数据。** 分区方案（时间×标的 vs 时间×因子）一旦定错，TB 级数据重分区代价极高。高频因子常按"时间×因子名"存横截面、"时间×标的"存时序，两套并存。
4. **时间戳双记 + PTP 对时。** 交易所时间、本地接收时间、入库时间分开存，精度到纳秒；跨机房用 PTP 而非 NTP。时间戳不对齐，所有高频因子和回测都是错的。
5. **行情先入内存再异步落盘。** 写入做批量化，别让落盘 IO 反压到策略链路。
6. **禁止未来函数（look-ahead）。** 因子库要支持 point-in-time 快照（ArcticDB 的 bitemporal、或自建版本表），财务数据用公告日期而非报告期日期。
7. **容量按 3~5 年算。** 按 A 股全市场 L1/L2 日增 20~50GB 估算，3 年就是 20~50TB 量级；再叠加因子库（因子数 × 标的 × 频率）通常比原始行情更大。留 2~3 倍余量，并设计好冷热分层。
8. **压测必须用你自己的数据和自己的查询。** 所有公开基准（含本文引用的）都是特定场景下的厂商自测，选型前用真实 L2 数据跑一轮端到端压测，再签合同。

## 七、选型决策树

| 如果你的情况是…… | 那就选 |
|---|---|
| 端到端时延要求 < 1ms，做真高频 | 数据库不进关键路径（内存状态机 + 内核旁路），研究侧 **kdb+ / KDB-X** 或 **DolphinDB** |
| 毫秒~秒级策略，A 股，做 L2 高频因子 | **DolphinDB**（主力）+ PostgreSQL（账务）+ Parquet 归档 |
| 分钟级 / 日频，团队 Python 为主，预算有限 | **ClickHouse** + **ArcticDB** + PostgreSQL |
| 规模不大（< 5TB），想少维护一套系统 | **PostgreSQL + TimescaleDB**，或 **QuestDB** |
| 已有 kdb+ 团队和许可 | 继续 **kdb+**，不要为了换而换；新增的因子平台可考虑 KDB-X 的 Python 接口降低门槛 |
| 只要做系统监控 / 运维指标 | InfluxDB 或 Prometheus，别拿它当行情库 |

---

> **最后一句判断**：如果你现在还不确定规模，就按方案 A 起步——把 DolphinDB 当作行情与因子的"中枢"，PostgreSQL 守账务，热路径自己写内存状态机。这三件事边界清晰，任何一块未来想换掉都不会推倒重来。反过来，如果你打算"用一个数据库解决毫秒级读写"，那基本可以预判项目会在数据量上到 TB 级或策略频率提到秒级以内时重构一次。
